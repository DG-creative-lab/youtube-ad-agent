# Campaign agent architecture

Updated 6 November 2026 · Proposed for the ElevenLabs application. The product brief defines the two Text to Speech creatives and viewer task. This plan defines the system boundaries. [Product brief](product-brief.md) · [Build plan](build-plan.md) · [Design direction](design-direction.md)

## Decision

Persist the campaign conversation separately from model tool turns. Each buyer message starts a bounded run; the final reply or clarification is committed with its terminal result and any draft change. Pin conversation ownership to actor, client, brand, campaign and model. Follow-ups use the current campaign revision and up to 20 recent dialogue messages within an 8 KB serialized budget, marked when earlier context is omitted. Preflight the complete provider JSON against the 32 KB transport cap before reserving a request, removing oldest complete dialogue messages and then tool pairs as needed; mark both kinds of omission and retain the full application evidence. Keep the current buyer request intact. An input that still cannot fit is rejected as a known local failure with zero provider calls. Dialogue is context, not approval authority or a verified replacement for application state. Retain the full transcript and exact run references for history. Retry the same operation ID to recover the same message/run. Reject a stale last-message reference; an accepted follow-up supersedes unfinished work in that conversation and prevents its late results from writing. Older placement runs are migrated into the transcript without rewriting their drafts or receipts.

Replies use constrained topics and clarification reasons. The application renders factual wording, with approval status resolved against the current package; no free model text can claim a draft save, approval, export or launch. Legacy unconstrained reply records are retained but projected as needing verification on chat and run reads, and excluded from factual dialogue context. New turns may adopt the current server prompt version without changing the conversation's model or limits; prior runs remain pinned to their original settings.

Keep execution driven by the existing sequential HTTP commands for this slice. Reopening a conversation reads saved progress and offers resume; it does not silently dispatch a provider request. SSE notifications, token streaming and a background worker are later capabilities and do not change the campaign command or conversation contracts.

8 November update: build an LLM-led tool loop, starting with placement discovery. A model picker beside the request composer selects the conversation's main model. Persist its model, scope and routing policy on the server and pin them on each run. Simulated responses remain the zero-cost default and are explicitly labelled; the recorded walkthrough remains compatible with existing runs.

The main model interprets the request and chooses among campaign tools based on their results. The Python harness validates tool names and inputs, current grants, revisions and budgets, then executes one bounded tool at a time. It does not prescribe a single semantic tool sequence. Unknown, incomplete or denied results return as structured observations so the model can recover within its allowance. A missing material business choice can end in a clarification; a saved draft ends at package review.

Configure specialist routing before a run and apply it at each tool dispatch. Placement classification uses a `PlacementClassifier` port automatically, with simulated decision responses for this slice. Jev is a probabilistic classifier, not an authority or a substitute for exact code. Counting, deduplication, source validation, revision checks and persistence stay in Python. Users choose the main model, not a classifier for every task. Live Jev remains disabled until a separately configured budget and evaluated routing policy exist. Public YouTube API output stays in its permitted search/review workflow; classifier inputs are authored fixtures or independently supplied catalogs with provenance.

Persist each inference reservation and receipt before executing its requested tool. Commit a tool's campaign change and result together. Unknown request outcomes consume that request's allowance and are not automatically redispatched. Pin the initial campaign revision and immutable catalog, bound the total turns and input/output sizes, recheck scope before dispatch and save, and keep approvals outside the model's tool set. The first vertical slice must show different model-selected tool paths, automatic classifier use, an ambiguous catalog item retained for review, and restart without duplicate inference or drafts. Later capabilities reuse this loop and the existing application commands.

Use a modular monolith with a Python backend and SQLite. Keep domain commands, approval rules and durable state in the application. Give the agent typed tools for planning, discovery, production, handoff and review. Connect providers through ports where their capabilities differ. Build the first runtime as a small in-process Python loop behind `AgentRuntime`, with recorded model responses behind `ModelInference` for the offline walkthrough. Adopt individual runtime patterns as the workflow needs them. [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) · [OpenRouter client tool calling](https://openrouter.ai/docs/guides/features/tool-calling)

Keep the existing HTML, CSS and JavaScript placement screen for the first `Save to campaign` slice. It calls the Python backend through a same-origin JSON API. Build the fuller planner in React and TypeScript when the brief, placements, creative previews, approvals and review need a shared workspace. Its client state handles navigation, forms and display. The Python commands remain the source of truth for campaign revisions, approvals and results. Keep the viewer comparison as a small HTML, CSS and JavaScript page using the same backend for versioned content and events. The planner and viewer share brand tokens and have separate layouts.

The client organization owns the tenant. A tenant can have several brands and grant its staff or an agency access to specific work. Scope ownership and application commands before adding more durable records. The local POC can resolve a seeded operator and client, then the hosted MVP can resolve authenticated members through an identity adapter. [Tenancy and growth plan](tenancy.md)

The primary flow starts with a request such as “Prepare a UK YouTube test for ElevenLabs Text to Speech using our approved material.” The agent loads the approved brief and brand policy, proposes viewing contexts, gathers placement candidates, prepares two cuts and matching destinations, and presents a campaign package. It chooses tools and follows up on their results within the mandate. The buyer sets the goal and reviews the resulting package once. Ask during preparation only when the application cannot resolve a material decision from approved context, or when the next action requires explicit authority. The product saves progress while the browser is closed and shows the next useful action when it reopens. The POC uses manual Google Ads handoff, real local viewer activity and labelled sample delivery. The agent can propose a follow-up test from those observations and any buyer corrections.

## Tool dispatch

The web UI and agent tools call the same application commands. Give the runtime structured tools for outcomes such as getting campaign delivery or saving a draft package. For agent calls, the application resolves tenant, brand and campaign scope from the saved run and checks the mandate before dispatch. Ad adapters own native IDs, field mapping, pagination and provider-specific retry or reconciliation. Tool results carry structured status and evidence references so a worker can distinguish an empty report, a partial report and an unavailable capability.

Start with one in-process runner and an explicit registry of the campaign tools it may request. Load scoped context, send the allowed tool schemas to the model, validate and dispatch requested calls through the application, then return their results to the model. Keep tool calls sequential in the first slice. End preparation when the application has saved a reviewable package, the run needs a buyer decision, a bound is reached, or recovery requires attention. Set a turn and time limit and check cancellation before dispatch and before saving a result.

Record the run, its scope and committed steps in SQLite. Use a stable command identity for any draft write that can be retried, and commit its receipt with the draft change. The application can resume from that receipt after an interruption. Keep a provider's transcript separate from the product's record of what happened. Add capabilities such as parallel specialists, scheduling or richer session management when a workflow needs them. Evaluate a Python-native runtime library only if a measured problem justifies the dependency and it can use the same commands, scope checks and recovery tests.

Keep policy checks and the dispatch receipt in the application. A preview shows the proposed change. Only a valid grant can queue the matching external effect. Record whether the provider call was attempted and what the provider confirmed. Verify rejection through the real dispatcher with a fake adapter and assert zero provider calls.

## How the agent learns

Brand knowledge is the approved reference for a brand within a client tenant. Save a new revision when an authorized editor changes a brief, rule or playbook. Record the revisions used for a campaign so the buyer can reconstruct the decision. Before a write, check the rules currently in force and request a revised package if a change invalidates the approved one. For launch-critical rules, enforce the check in product code.

Learning memory changes what the agent proposes on its next run. Store explicit user corrections with their intended scope. Treat inferred preferences and performance explanations as provisional. A finding records the brand, campaign and creative revisions, metric, reporting level, period, evidence and uncertainty. Let the buyer inspect, correct or retire it. Agents can propose a playbook update through the normal review flow. A finding on its own grants no permission and changes no brand rule. Harness session history remains available for resuming work. Start both product stores in SQLite.

For example, a report shows that the editing ad attracted visits while few visitors completed both voice samples. Compare completion per tagged arrival by ad version where the data supports it. If the pattern warrants investigation, save a hypothesis and propose testing a shorter second sample while holding the ad and destination flow constant. A second run retrieves the hypothesis and explains why it chose the test. Missing or aggregated placement rows stay unknown at the video level. Observed differences can guide an experiment, while a controlled comparison is needed to claim the creative change caused improvement. Keep platform delivery, viewer events and simulated data distinct. [Google placement reporting](https://developers.google.com/google-ads/api/docs/reporting/placement-views)

## Mapping the campaign loop to Superagent

| Superagent pattern | Campaign application |
| --- | --- |
| Source → Trigger → Assessor | A buyer request, correction or a deduplicated report update enters intake. The assessor decides whether it warrants a preparation or review assignment. The report itself grants no activation authority. |
| Ticket + Mandate → Assignment | A bounded job carries its brand, campaign, approved reference versions, tools and spending scope. A specialist can research placements or analyze results under a narrower assignment. |
| Engine, Policy and Repositories | Our application owns campaign state, versioned knowledge, evidence, learning memory and effect approval. The selected runner requests scoped tools and returns proposals. |
| Queued effects after a committed decision | Use the same pattern for campaign actions. The prototype's Outbox handles replies. Our application adds a separate queue for ad operations and records provider results against the exact approved package. |

## Reporting and activation adapters

Use API queries through `CampaignReporting` for scheduled, repeatable measurements. A scoped MCP adapter can support ad hoc investigation through the same reporting boundary. Google's published MCP server is read-only. Store the provider account, campaign and available ad identifiers, date range, report level and coverage so a review can tell where the campaign ran and how much of it is observable. A configured placement and a reported impression are separate facts. [Google Ads MCP server](https://developers.google.com/google-ads/api/docs/developer-toolkit/mcp-server) · [Placement reporting](https://developers.google.com/google-ads/api/docs/reporting/placement-views)

Use `CampaignActivation` to validate, create paused, verify and, under an explicit grant, enable or change a campaign. A buyer can approve a package once for the named account, revision, actions, budget ceiling and validity period. The application checks that grant at dispatch and the connector alone holds the provider credentials. On an uncertain write, stop and reconcile against the provider before retrying. Persist request identifiers, remote resource IDs and verified state. The buyer sees partial or unknown outcomes in the same review view.

Google Ads API support depends on campaign type. Standard Video campaign creation and updates generally require a manual path. Demand Gen supports API creation and YouTube channel controls. Confirm the required individual video and channel placement targeting for the exact writable campaign configuration before relying on it. Selecting a surface such as YouTube in-stream is a different capability from selecting a specific video. If the connector cannot preserve the approved targeting, surface the constraint and keep the manual export for the contextual pilot. Verify reporting granularity separately. [Video API limitations](https://developers.google.com/google-ads/api/docs/video/overview) · [Demand Gen API](https://developers.google.com/google-ads/api/docs/demand-gen/overview) · [Demand Gen channel controls](https://support.google.com/google-ads/answer/15973205)

## Autonomy and recovery

The buyer gives the agent a brief and a mandate. The mandate defines the workspace, data sources, approved brand material, actions and cost limits. The agent can choose search phrases, divide research and creative work, prepare drafts, render locally, verify destination links and assemble a review package. It asks about missing rights, irreconcilable constraints or a decision that authorizes publication or spend. A subagent receives the minimum data and tools for its assignment and returns a proposed result. Start with placement research and creative review as the two candidates for delegation. The parent run owns the package.

Keep campaign records and a short activity history in SQLite. Persist job intent before work begins and record outputs or failure with their request identifiers. On restart, resume from the last completed product step. In a later integration, if Google receives a write and the network drops before the response, reconcile provider state before attempting that write again. A browser refresh, runtime change or model session reset must preserve the draft and its evidence.

For user-authored tools, start with a typed recipe such as “Compare reported placements with the approved plan and show any out-of-plan delivery.” The recipe has explicit inputs, outputs, and an allowlist of existing capabilities. Save the version and let the agent use it under the same run permissions. Add code or an external MCP tool only through a separately enabled and scoped connector.
